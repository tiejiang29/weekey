# Weekey — Home Assistant 自定义集成

把 Weekey（微开 / 熊猫微开等基于 weekey SaaS 的小区门禁）的**远程开门**接入 Home Assistant，
每个门禁一个 `switch` 实体：打开即下发开门命令，并在 3 秒后自动回落到关闭状态。

> **状态：已在 Home Assistant 2026.6.4（Container）上跑通，并实测到门被实际打开。**
> 配置流、会话校验、门列表、实体创建、点按开门全部验过；点按之后厂商 `unlocklog` 里生成了
> 对应门的记录，业主本人也现场确认了门开启。
> **但请注意：实体那个 `on` 仍然是合成状态**，它来自平台的受理回执，不是门锁的反馈——
> 厂商不提供任何锁状态查询。详见下方《实体》与《行为约束》。
> 代码按 2026.6.4 的 API 编写（`voluptuous` schema、`runtime_data`、`OptionsFlowWithReload`），
> 升级 HA 大版本时请留意这些依赖点。

## 这个集成的前提，请先读完

Weekey **没有对外的登录接口**。它的小程序开门页跑在微信 webview 里，会话由微信网页授权
（`snsapi_base` + 服务商代公众号授权）建立，之后所有请求只凭一个 `PHPSESSID` cookie。

因此：

- 你**必须手工抓一次 cookie 并粘贴**到配置流里。没有 OAuth、没有 API Key、没有自动登录。
- **无法自动续期。** 换取 openid 需要微信客户端签发的一次性 code，以及厂商服务器上的
  `component_access_token`，两者都不可能出现在 Home Assistant 上。
- 会话过期后集成会进入"需要重新认证"状态，UI 里会提示你重新粘贴 cookie。

实测一个会话至少连续可用 **69 小时**（跨小程序重启、跨负载均衡后端切换），但这不是保证，
上限没有测出来。

## 安装

### HACS

1. HACS → 自定义仓库，添加 `https://github.com/tiejiang29/weekey`，类别选 **Integration**。
2. 搜索 "Weekey" → 下载。
3. 重启 Home Assistant。

### 手工

把 `custom_components/weekey/` 整个目录放进你的 `/config/custom_components/`，重启 HA。

## 抓取 PHPSESSID

在电脑上用微信打开小程序的门列表页，用任意抓包工具（Reqable / Charles / mitmproxy /
浏览器 DevTools）找到对 `s.weekey.cn` 的请求，复制请求头里的：

```
Cookie: PHPSESSID=<这里>
```

粘贴到配置流里即可（带 `PHPSESSID=` 前缀的整段也能识别，会自动剥离）。

抓包文件请当作**凭据**保管：它同时包含你的会话 cookie，而且这类页面通常会带上你的姓名、
手机号和小区信息。分享或提交 issue 前删掉。

## 配置

设置 → 设备与服务 → 集成 → 添加集成 → **Weekey**，只需填一项：

| 字段 | 说明 |
|---|---|
| PHPSESSID | 小程序会话 cookie，唯一凭据 |

集成会用它向 `s.weekey.cn` 验证会话，成功后从响应里解析出账号 ID 作为该集成条目的唯一标识，
所以重复添加会被拒绝。**账号 ID、小区标识都不会写进本仓库或日志。**

添加完成时，集成会把当前所有可用的门**默认全部启用**（电梯/呼梯类设备除外）。想只留几档，
在集成卡片上点 **配置** 取消勾选，也可以在那里调整刷新间隔（默认 15 分钟，最低 5 分钟）。
把全部门都取消勾选是允许的——那样就没有实体，这是有意的，不会再静默出现。

## 实体

| 实体 | 说明 |
|---|---|
| `switch.<门名>_open` | 打开=下发开门命令，3 秒后自动关闭 |
| 设备可用状态 | 来自平台的设备在线标记；门禁控制器离线时实体显示为"不可用" |

**`on` 是合成的状态，不是门的状态。** 它表示"平台刚刚受理了一次开门命令"，**不代表门现在开着、
也不代表锁真的通电了**（厂商没有任何锁状态查询接口）。3 秒后自动回落只是为了让界面不卡住。
把它当成瞬时开关来用，**不要写"如果这个 switch 是 on 就说明门开着"这类自动化**。
同理，`turn_off` **不会去关门的任何部件**，它只是清掉这个合成状态——厂商不存在"关门"这个操作。

**为什么不做成 `lock` 实体。** Weekey 不提供任何"当前是开还是关"的查询接口，一个状态永远是
unknown 的 lock 会向自动化和语音助手谎报状态。这里用 switch 只表达"我按了一下"，语义是诚实的。

## 行为约束（有意为之）

- **超时和 5xx 一律报"开门结果未知，不要重试"，并把开关留在 off。** 请求可能已经到达设备，自动重试等于再开一次门。
- **每个门 10 秒冷却 + 单飞锁**，防止连点，也防止自动化把电控锁硬件连续驱动。冷却比自动复位（3 秒）
  长得多，所以"开关已经灭了但再开会提示太频繁"是预期行为。
- **返回码分两层判断，且两层都来自平台、不是设备**：外层 `code==1` 只代表请求被受理，
  内层 `open.err_code==0` 代表平台报告开门成功。**厂商可能先记账再下发，也可能下发失败仍留记录**，
  所以这两个值都不等于"锁通了电"。要确认这一点只能现场目视。
- **电梯/呼梯类设备（type 1/2/4）不会被暴露成开门开关**，即使有人手改了存储文件。这个接口
  (`unlock_new?floor=N`) 同时服务乘梯和呼梯，误当门开等于叫了一趟电梯。

## 安全建议

**不要把这个集成接入语音助手，也不要让不可信的自动化直接按它。**

Home Assistant 对 `switch` / `button` 这类实体没有内置的 PIN 或二次确认（唯一有验证码路径的是
`lock` 实体的 `code_format`，但那要求实现状态回读）。也就是说，任何能调用 `switch.turn_on` 的东西
——包括仪表盘上误触、以及任何被注入到你家的自动化——都能开门。而且换成 switch 之后有个**新增**风险：
语音助手和"状态即事实"类自动化会把那个合成的 `on` 当成门的状态来读。建议：

- 只放在需要登录才可见的仪表盘上，不要暴露给 Assist / Google / Alexa。
- 不要用这个实体做"门开着没"的判断条件，它回答不了这个问题。
- 开门记录会全部记在**你的** Weekey 账号名下，分享 HA 给家人前先想清楚这一点。

## 已知限制

- 门列表来自平台的"一键开门"面板接口，它**不是权限全集**——如果你有门不在这个列表里
  （例如需要切换房间、或扫码进入的门），本集成不会自动发现它们。
- 中文门名经 HA slugify 后 `entity_id` 可能不稳定，建议配置完成后在 UI 里给设备改成英文名。
- 未做：访客限时凭证、人脸管理、电梯调度、监控视频。
